# 前端对接说明：请求签名 & 令牌刷新

本文档给前端（`web/`）对接两个后端能力：
1. **签名鉴权中间件**（`POST /api/utils/sign`）—— 外部测试签名用：请求需携带经 HMAC-SHA256 签名头，由中间件校验，通过后返回成功。
2. **令牌刷新** `POST /api/auth/refresh` —— 用有效会话令牌换取新令牌、延长会话有效期。

所有接口位于 `baseURL=/api` 下。`/auth/refresh` 需 `Authorization: Bearer <token>`；`/utils/sign` 需 **登录 + 签名头**（见下文）。

---

## 一、签名鉴权 `POST /api/utils/sign`（外部测试签名）

### 用途
该接口用于**外部联调/验证签名算法**。请求在**登录之后**还需携带一套签名头，由后端**签名中间件**（`internal/httpapi/sign_middleware.go` 的 `signAuth`）校验，通过后才进入 handler（返回成功）。

### 请求链
```
登录获取 Bearer token
   ↓
请求头携带  Authorization: Bearer <token>
          + X-Timestamp: <Unix 秒>
          + X-Nonce:     <随机串>
          + X-Signature: <hex HMAC-SHA256>
   ↓
[中间件 withAuth] 校验登录
   ↓
[中间件 signAuth] 校验签名（如下）
   ↓
进入 handler 返回成功
```

### 签名规则（规范串 + HMAC-SHA256）
规范串按以下顺序、以 `\n` 连接（**固定结构**）：

```
规范串 = METHOD大写
       + "\n" + path
       + "\n" + query
       + "\n" + body(请求体原文)
       + "\n" + timestamp(X-Timestamp 原值)
       + "\n" + nonce(X-Nonce 原值)
```

```
signature(hex) = hex( HMAC-SHA256( key = 共享密钥, message = 规范串 ) )
```

要点：
- METHOD 用**大写**；`path` 为 URL 路径，`query` 为原始查询串（无则空）。
- `body` 必须是**请求体原文**（客户端签名时用与服务端完全一致的字节）。
- 共享密钥 = 后端环境变量 **`KS_SIGN_SECRET`**，客户端须与其一致才能算出相同签名。
- **时间戳新鲜度**：`|now - X-Timestamp|` 超过 ±5 分钟即拒绝。
- **nonce 防重放**：同一 nonce 在窗口内重复使用即拒绝。

### 响应
校验通过返回 200（`timestamp`/`nonce` 原样回显，便于确认）：
```json
{
  "ok": true,
  "timestamp": 1730000000,
  "nonce": "abc123"
}
```
校验失败返回 **401**（缺失签名头 / 时间戳超差 / nonce 重放 / 签名不一致）。

### 可验证示例
假设请求体为 `{"id":1}`、共享密钥为 `my-secret-key`：

| 组成 | 值 |
|------|-----|
| METHOD | `POST` |
| path | `/utils/sign` |
| query | ``（空） |
| body | `{"id":1}` |
| timestamp | `1730000000` |
| nonce | `abc123` |

规范串：
```
POST\n/utils/sign\n\n{"id":1}\n1730000000\nabc123
```

### 前端 TypeScript 参考实现（Node 端示例）
```ts
import { createHmac } from 'crypto' // 浏览器侧改用 WebCrypto

export function signRequest(o: {
  method: string
  path: string
  query?: string
  body: string
  secret: string
}): { timestamp: number; nonce: string; signature: string } {
  const timestamp = Math.floor(Date.now() / 1000)
  const nonce = crypto.randomUUID()
  const canonical = [
    o.method.toUpperCase(),
    o.path,
    o.query ?? '',
    o.body,
    String(timestamp),
    nonce,
  ].join('\n')
  const signature = createHmac('sha256', o.secret)
    .update(canonical)
    .digest('hex')
  return { timestamp, nonce, signature }
}
```

```ts
// 调用示例
const { timestamp, nonce, signature } = signRequest({
  method: 'POST',
  path: '/utils/sign',
  body: '{"id":1}',
  secret: KS_SIGN_SECRET,
})
const res = await api.post('/utils/sign', '{"id":1}', {
  headers: { 'X-Timestamp': timestamp, 'X-Nonce': nonce, 'X-Signature': signature },
})
console.log(res.data) // { ok: true, timestamp, nonce }
```

## 二、令牌刷新 `POST /api/auth/refresh`

### 用途
在会话仍有效时，用当前的 `Bearer` 令牌换取 **一个新令牌** 并 **延长会话有效期**（TTL 重新按 `KS_SESSION_TTL_HOURS`，默认 168 小时 = 7 天），旧令牌随即作废。适用于“有效期临近、界面仍活跃时主动续期”，避免用户掉线。

### 请求
无需请求体，只需在头中携带当前令牌：
```
Authorization: Bearer <当前有效token>
```

### 响应
```json
{
  "token": "b3f8c2a1...（新令牌，64 位 hex）",
  "expires_at": "2025-01-01T00:00:00Z"
}
```

### 刷新原理
```
[请求] Authorization: Bearer <旧token>
        ↓ withAuth 中间件校验会话存在且未过期（过期则 401）
[后端] ① 取当前用户 userID（来自上下文）
       ② 用 旧token 的 sha256 哈希 删除旧 Session 记录
       ③ 生成新随机 token，存新 Session(TokenHash, userID, 过期=now+TTL)
       ④ 返回新 token
```

- 令牌以 **明文 64 位 hex** 下发；数据库中仅存 **`sha256(token)` 哈希**（见 `internal/httpapi/util.go` 的 `hashToken`）。
- 刷新后 **旧令牌立即失效**（Session 记录被删除），因此**不要把刷新前后的令牌混用**。
- 因为是**轮换（rotation）**模式，同一令牌不可重复刷新——每次刷新都签发全新令牌。

### 重要边界
- `/auth/refresh` **要求令牌当前仍有效**（未过期）。它用于**主动续期**，**不能**救回已过期的会话——过期会话需重新走 `/auth/login`。
- 因此前端应在**过期前**（而非收到 401 后）主动刷新。

### 前端使用建议（配合现有 401 处理）
当前 `web/src/api/client.ts` 在收到 401 时会清空 token 并跳转登录页。若要做“静默续期”，建议：

1. 拦截 401 时，先用 `login` 兜底（现逻辑保持不变）；
2. 若想续期：在过期前主动调用 `/auth/refresh`，成功后用新 token 覆盖 `kianshu_token`（见 `web/src/store/session.ts` 的 `setToken`），并让请求拦截器继续用新 token；
3. 刷新失败（401/网络错误）时，再走 `clearSession()` + 跳登录。

> 注意：因每次刷新都轮换令牌，若同时发起多个并行请求各自触发刷新，会产生多个互相作废的会话。建议**对刷新操作加锁 / 串行化**（单实例刷新，成功后统一广播新 token）。
